# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Deliver the MVP Requester Portal for TokTickIT enabling end users (Requesters) to create support tickets with attachments, view and manage their submitted tickets, and maintain clear ticket ownership isolation using a development requester testing context prior to full authentication in Lab 3.

## 2. Stakeholder Request Interpretation
The IT department needs a functional, responsive web interface for requesters to log IT support tickets, provide metadata and evidence attachments, track their own ticket list, and view ticket details. Since real authentication is deferred to Lab 3, a simulated Development Requester Selector must be provided to test multi-user ticket ownership.

## 3. Scope
### Included
- Development Requester selection and context switching (testing mechanism).
- Create Ticket screen with backend-generated Ticket Number and field validations.
- My Tickets screen with search, filtering, sorting, and pagination.
- Requester Ticket Detail screen (read-only mode).
- Attachment lifecycle: upload permitted types, download active files, and soft removal with reason.
- Data and ownership isolation between different requesters.
- Zen Green UI theme and responsive layout for Desktop, Tablet, and Mobile viewports.

### Excluded
- Real authentication, passwords, tokens, sessions, and role-based access control (RBAC).
- IT Staff queues, ticket claiming, reassignments, and changing IT Priority.
- Public Comments, Internal Notes, and Actions Taken.
- Post-creation ticket lifecycle transitions (resolving, closing, reopening, cancelling).
- Administrative interfaces for managing categories and related systems.

## 4. Functional Requirements
- **FR-01**: The system must provide a Development Requester selector listing only active requesters.
- **FR-02**: The system must allow the requester to submit a ticket with Category, Related System, Requested Priority, Summary, Description, and up to 5 attachments.
- **FR-03**: The system must automatically generate a unique, non-editable Ticket Number upon creation.
- **FR-04**: The system must display a paginated list of tickets owned exclusively by the currently selected requester.
- **FR-05**: The system must support searching tickets by Ticket Number or Summary, and filtering by Category, Priority, and Status.
- **FR-06**: The system must display ticket details in a read-only format for the ticket owner.
- **FR-07**: The system must allow adding new attachments to an existing ticket up to the active limit of 5 files.
- **FR-08**: The system must support soft removal of attachments requiring a mandatory reason.
- **FR-09**: The system must block download and preview of soft-removed attachments while preserving metadata.
- **FR-10**: The system must reject unauthorized direct access to tickets or attachments belonging to another requester.

## 5. Business Rules
- **BR-01**: Official Ticket Number is generated by the backend and must follow a unique structured format (e.g., `TKT-YYYY-XXXXXX`).
- **BR-02**: A newly created Ticket must always have `currentStatus` set to `NEW`.
- **BR-03**: The Development Requester selector is strictly a testing harness and does not represent secure authentication.
- **BR-04**: Inactive Requesters must be excluded from the Development Requester selection dropdown.
- **BR-05**: Ticket Summary is required (min 5, max 100 characters). Description is required (min 10, max 2000 characters).
- **BR-06**: Permitted attachment file types are strictly limited to `image/jpeg`, `image/png`, `image/webp`, and `application/pdf`.
- **BR-07**: Maximum file size per attachment is 5 MB.
- **BR-08**: A Ticket can have a maximum of 5 active attachments at any given time.
- **BR-09**: Attachment deletion is strictly soft-delete (`isRemoved = true`), requiring a mandatory removal reason string.
- **BR-10**: Soft-removed attachments cannot be downloaded, previewed, or restored.
- **BR-11**: Data Isolation: Requester B must not be able to view, query, or modify tickets or attachments belonging to Requester A.

## 6. UI Specification Summary
- **Palette**: Zen Green Theme (Primary: `#006B3C`, Secondary: `#0B7A46`, Pale Green: `#EAF6EF`, Background: `#F5F7F6`).
- **Layouts**: Responsive grid supporting Desktop (≥992px), Tablet (768–991px), and Mobile (<768px).
- **Feedback**: Immediate field-level validation errors displayed directly under the affected input; preserved form state upon API failure.

## 7. Data Changes
- **Models**: `RequesterUser`, `Category`, `RelatedSystem`, `Ticket`, `Attachment`.
- **Relationships**: 1 RequesterUser to Many Tickets; 1 Ticket to Many Attachments; 1 Category to Many Tickets; 1 RelatedSystem to Many Tickets.
- **Indexes**: Unique index on `Ticket.ticketNumber`, index on `Ticket.requesterId`, index on `Ticket.createdAt`.

## 8. API Contract Summary
- `GET /api/requesters`: Returns active requesters.
- `GET /api/categories`: Returns active categories.
- `GET /api/related-systems`: Returns active related systems.
- `GET /api/systems`: Returns active related systems.
- `POST /api/tickets`: Creates a ticket for the requester identified by `x-requester-id`.
- `GET /api/tickets`: Returns paginated, filtered, sorted tickets for the requester identified by `x-requester-id`.
- `GET /api/tickets/:id`: Returns details of an owned ticket.
- `POST /api/tickets/:id/attachments`: Uploads an attachment for an owned ticket.
- `GET /api/attachments/:id`: Returns metadata for an owned attachment.
- `DELETE /api/attachments/:id`: Soft-removes an attachment with a mandatory reason (sent in the request body).

## 9. Acceptance Criteria
- **AC-01**: Given valid ticket fields, when the requester submits the form, then a ticket is saved in the database with `currentStatus = NEW` and a unique Ticket Number is returned.
- **AC-02**: Given an unselected Development Requester, when opening the app, then the selector screen is displayed.
- **AC-03**: Given Requester A is selected, when requesting a ticket owned by Requester B, then the API returns 403/404.
- **AC-04**: Given an attachment file > 5 MB or invalid MIME type, when attempting upload, then it is rejected with a clear field-level error.
- **AC-05**: Given an active attachment, when soft-removed with a valid reason, then `isRemoved` is set to true, metadata remains visible, and download attempts return 404/410.
- **AC-06**: Given search/filter parameters, when querying My Tickets, then only matching tickets belonging to the current requester are returned.
- **AC-07**: Given the Development Requester list is being fetched, when the Selection screen is open, then a loading indicator is shown and Continue is disabled until the fetch resolves.
- **AC-08**: Given no active Development Requesters exist, when the Selection screen loads, then an explicit empty-state message is shown and Continue remains disabled.
- **AC-09**: Given the `/api/requesters` request fails, when the Selection screen loads, then a safe failure message is shown instead of a blank or broken screen.
- **AC-10**: Given multiple tickets are created concurrently, when Ticket Numbers are generated, then every Ticket Number remains unique.
- **AC-11**: Given a requester ID belongs to an inactive Development Requester, when it is sent directly to the API, then ticket creation and attachment upload return HTTP `403 Forbidden`.
- **AC-12**: Given a file is uploaded as an attachment, when its metadata is later displayed, then the requester's original file name is shown — never the internally generated storage file name.

- [x] All acceptance criteria validated with passing automated tests (Unit, API, UI, E2E).
- [x] Responsive layout verified at Desktop, Tablet, and Mobile viewports without overflow.
- [x] Idempotent seed data loads 4 categories, ≥6 related systems, ≥4 active requesters, and ≥1 inactive requester.

## 11. Assumptions and Decisions
- Requester identity is passed via custom header `x-requester-id` for Lab 2 API requests to simulate context.
- Files are stored locally in `server/uploads/` with sanitized, unique filenames.
